# JobFit

사용자 조건과 가중치를 반영해 채용공고 적합도와 추천 근거를 제공하는 AI 기반 맞춤형 채용공고 추천 서비스

- **배포**: https://jobfit-kjih.onrender.com
- **API**: https://jobfit-api-xdu0.onrender.com

## 데모

https://github.com/user-attachments/assets/4867fcc1-f7cc-417c-981e-d97b0d84441e



기술·경험 중심(40/30/20/10)에서 우대사항 중심(20/20/50/10)으로 가중치를 바꾸면 1위와 2위의 점수 차이가 19.0점에서 7.4점으로 줄어듭니다. 순위가 바뀌는 사례는 아래 가중치 변경에 따른 추천 순위 변화 표를 참고하세요.

## 문제 정의

채용 시즌에 지원자는 수십 개의 공고를 직접 읽고 자신의 경험과 하나씩 대조해야 합니다.
기존 채용 플랫폼의 추천은 키워드 일치 기반이라 "왜 이 공고가 추천되었는지",
"내 경험 중 무엇이 부족한지"를 알기 어렵습니다.

JobFit은 공고의 요구사항을 구조화하고, 사용자가 직접 설정한 평가 기준에 따라
적합도를 계산한 뒤 **판단 근거를 함께 제시**합니다.

실제 출력 예시입니다. (2026년 8월 기준 데이터셋)

```
OCI정보통신(주) — 사내 솔루션 개발 및 기능 개선 담당
지원 가능 · 종합 56.7점 (기술 66.7 / 경험 66.7 / 우대 0.0 / 자격증 100.0)

적합한 점
  Java 충족 — HopeTail-BE, KakaoMCP, JobFit 프로젝트에서 사용
  Spring Boot 충족 — HopeTail-BE, KakaoMCP, JobFit 프로젝트에서 사용
  OPIC 충족 — 보유 자격증 목록에 포함

부족한 점
  React 미보유
```

## 핵심 차별점

- **사용자가 평가 기준을 조정** — 기술/경험/우대사항/자격증 가중치를 직접 설정하고, 변경 시 추천 순위가 어떻게 달라지는지 확인
- **필수 조건과 선호 조건 분리** — 필수 조건 불충족 시 높은 기술 점수에도 상위 노출되지 않음
- **근거 기반 판단** — 점수만 제시하지 않고 공고 요구사항과 사용자 프로젝트 경험을 연결해 표시

### 가중치 변경에 따른 추천 순위 변화

동일한 검증용 공고를 서로 다른 가중치로 평가한 결과입니다. (2026년 8월 기준, 이후 점수 로직 개선 전 수치)

| 순위 | 기술 40 / 경험 30 / 우대 20 / 자격증 10 | 기술 20 / 경험 20 / 우대 40 / 자격증 20 |
|---|---|---|
| 1 | OCI정보통신 56.7 | OCI정보통신 46.7 |
| 2 | 토스뱅크 46.7 | **킨코스코리아 35.5** |
| 3 | 킨코스코리아 39.2 | 위드네트웍스 30.1 |
| 4 | 위드네트웍스 31.7 | **토스뱅크 26.7** |

우대사항 비중을 높이면 토스뱅크가 2위에서 4위로, 킨코스코리아가 3위에서 2위로 이동합니다.
자격요건 충족도는 높지만 우대사항이 명시되지 않은 공고는 하위로 밀립니다.
기술 가중치를 높이면 Java/Spring 기반 공고가 상위로 이동합니다.
평가 기준이 바뀌면 추천 결과도 함께 달라진다는 것을 확인할 수 있습니다.

## 아키텍처

```
[React SPA]  ──HTTP──▶  [Spring Boot API]  ──▶  [PostgreSQL]
                              │
                              └──▶  [OpenAI API]
                                     · 공고 요구사항 구조화
                                     · 판단 근거 생성
```

평가 요청은 다음 순서로 처리됩니다.

```
POST /api/evaluations
  │
  ├─ JobRequirementExtractor    공고 원문 → 구조화 (캐시 우선, 실패 시 정규식 fallback, 개념어 필터)
  ├─ RequiredConditionChecker   경력·고용형태·마감일·직무 필수 조건 판정
  ├─ ScoreCalculator            기술·경험·우대·자격증 항목별 점수 산출 (별칭 매칭, 평가 불가 항목 제외)
  ├─ EvaluationWeight           사용자 가중치 적용 → 종합 점수 (제외 항목 가중치 재배분)
  └─ EvaluationReasoningGenerator  규칙 기반 매칭 결과를 받아 판단 근거 문장 생성
```

## 도메인 모델

```
JobPosting                     채용공고
├── source                     공고 출처
├── externalId                 출처별 공고 ID   ┐ 복합 유니크 제약으로
└── ...                                        ┘ 중복 수집 방지

UserProfile                    사용자 프로필
├── UserSkill        (1:N)     보유 기술
├── UserProject      (1:N)     프로젝트 경험 (사용 기술 포함)
├── UserCertificate  (1:N)     자격증 (등급·취득일 포함)
└── EvaluationWeight (1:1)     항목별 가중치 (합계 100 검증)

JobRequirementExtraction (1:1 with JobPosting)
                               LLM 추출 결과 캐시

JobApplication                 지원 완료 기록 (체크 시 생성, 해제 시 삭제)
├── userProfile      (N:1)     ┐ (user_profile_id, job_posting_id) 유니크 제약으로
├── jobPosting       (N:1)     ┘ 프로필·공고 쌍당 1건
└── appliedAt                  지원 완료 시각

EvaluationReasoningCache       판단 근거(checkPoints) 캐시
├── jobPostingId               ┐ (job_posting_id, user_profile_id) 유니크 제약으로
├── userProfileId              ┘ 공고·프로필 쌍당 1건 (연관관계 없이 ID만 저장)
├── profileHash                프로필 내용 해시      ┐ 하나라도 다르면 무효,
├── extractionHash             추출 결과 해시        │ 다시 생성해 같은 행을 덮어씀
├── reasoningPromptVersion     근거 프롬프트 버전    ┘
└── checkPointsJson            checkPoints (JSON 배열 문자열)
```

**보유 기술과 프로젝트 경험을 분리한 이유**

자기 신고 숙련도는 신뢰하기 어렵기 때문에 숙련도 필드를 두지 않았습니다.
대신 기술의 실제 활용 여부를 프로젝트 경험에서 역산합니다.

| 상태 | 판정 |
|---|---|
| 기술 보유 + 프로젝트 사용 이력 | 충족 (근거 제시 가능) |
| 기술 보유만 | 부분 충족 |
| 미보유 | 미충족 |

이 구조 덕분에 "Redis 충족 — HopeTail-BE에서 로그아웃 블랙리스트 구현에 사용"처럼
근거를 자동으로 도출할 수 있습니다.

## 적합도 판정 방식

### 1단계 — 필수 조건 판정

하나라도 충족하지 못하면 종합 점수와 무관하게 **지원 불가**로 분류합니다.

| 조건 | 판정 기준 |
|---|---|
| 경력 | 신입 지원자에게 최소 경력이 요구되는 경우 |
| 고용 형태 | 희망 고용 형태와 공고가 불일치하는 경우 |
| 마감일 | 지원 기간이 종료된 경우 |
| 직무 분류 | 공고 직무가 희망 직무와 무관한 경우 |

기술 적합도가 높아도 필수 조건에서 걸러지는 사례가 실제로 확인됩니다.

- **링크알파코리아** — 기술 스택과 도메인이 겹치지만 경력 5년 이상 요구로 지원 불가
- **누비랩** — 보유 기술과의 매칭도가 검증용 공고 중 최상위권이나 인턴 채용이라 지원 불가

### 2단계 — 항목별 점수와 가중치

필수 조건을 통과한 공고에 대해 항목별 점수를 계산하고 사용자 가중치를 적용합니다.

```
종합 점수 = Σ(평가된 항목 점수 × 가중치) / Σ(평가된 항목 가중치)
```

| 항목 | 계산 방식 |
|---|---|
| 기술 | 공고 필수 기술 중 보유 비율. 프로젝트 사용 이력이 있으면 100점, 보유만 하면 60점 |
| 경험 | 프로젝트별 필수 기술 매칭 비율의 최댓값 |
| 우대사항 | 공고 우대 기술 중 보유 비율 |
| 자격증 | 필수 자격증 중 하나라도 보유하면 100점, 우대 자격증만 보유하면 60점 (공고의 자격증 요구는 대부분 "A 또는 B" 형태) |

**기술명 매칭**

기술·경험·근거 생성은 모두 `SkillAliasNormalizer`를 거친 같은 기준으로 매칭합니다.

| 공고 표기 | 일치로 보는 사용자 보유 기술 |
|---|---|
| Spring Framework, Spring | Spring Boot |
| RDBMS, SQL | MySQL 또는 PostgreSQL |
| AI Coding Assistant 등 AI 코딩 도구 | Claude Code, Copilot, Cursor 중 하나 |

**평가 제외와 가중치 재배분**

공고에 평가할 근거가 없는 항목은 0점으로 처리하지 않고 평가에서 제외합니다.
필수 기술이 없으면 기술·경험을, 우대 기술이 없으면 우대를, 필수·우대 자격증이 모두 없으면
자격증을 제외하고, 제외된 항목의 가중치는 나머지 항목에 비례해 배분합니다.
모든 항목이 제외되면 점수를 매기지 않고 **정보 부족**으로 분류합니다.

## API

| Method | Endpoint | 설명 |
|---|---|---|
| POST | `/api/jobs` | 공고 등록 (중복 시 409)\* |
| GET | `/api/jobs` | 공고 목록 조회 |
| GET | `/api/jobs/{id}` | 공고 단건 조회 (없으면 404) |
| POST | `/api/jobs/{id}/re-extract` | 공고 요구사항 강제 재추출 (캐시 무시, LLM 실패 시 fallback 없이 실패)\* |
| POST | `/api/users/profile` | 프로필 등록 (기술·프로젝트·자격증·가중치 포함)\* |
| GET | `/api/users/profile/{id}` | 프로필 조회 |
| PUT | `/api/users/profile/{id}` | 프로필 수정 (가중치 제외, 기술은 lowercase·중복 제거)\* |
| GET | `/api/users/profile/settings` | 프로필 수정 가능 여부 (`editEnabled`) |
| PUT | `/api/users/profile/{id}/weights` | 가중치 수정 |
| DELETE | `/api/users/profile/{id}` | 프로필 삭제\* |
| PUT | `/api/users/profile/{profileId}/jobs/{jobId}/applied` | 지원 완료 표시 |
| DELETE | `/api/users/profile/{profileId}/jobs/{jobId}/applied` | 지원 완료 표시 해제 |
| POST | `/api/evaluations` | 전체 공고 평가 (적합도순 정렬) |
| GET | `/api/evaluations/{userProfileId}/jobs/{jobPostingId}` | 단건 평가 |

\* `PROFILE_EDIT_ENABLED=true`일 때만 허용되며, 미설정(기본값)이면 403을 반환합니다. 공개 배포 환경에서는 설정하지 않습니다.
공고 등록과 강제 재추출은 캐시를 거치지 않고 LLM 호출로 이어져, 반복 호출 시 API 비용이 발생하므로 같은 플래그로 막습니다. (시작 시 seed 적재는 서비스를 직접 호출하므로 영향받지 않습니다.)

## 테스트

핵심 판단 로직을 계층별로 검증합니다.

| 대상 | 검증 내용 |
|---|---|
| `JobRequirementParser` | 경력 조건 텍스트 파싱 (검증용 실제 공고의 경력 표기와 신입 허용 변형) |
| `JobRequirementExtractor` | 개념어 필터 (추출 직후와 캐시 조회 시 모두 적용) |
| `RequiredConditionChecker` | 경력·고용형태·마감일·직무 판정 |
| `SkillAliasNormalizer` | 기술명 별칭과 범주 매칭 |
| `SkillScoreCalculator` | 기술 매칭 3단계 (사용 이력 / 보유 / 미보유), 평가 제외 |
| `ExperienceScoreCalculator` | 프로젝트별 매칭 비율 (별칭 매칭 포함) |
| `CertificateScoreCalculator` | 필수·우대 자격증, OR 조건, 대소문자 무시 매칭 |
| `ScoreCalculator` | 평가 제외 항목 가중치 재배분 |
| `EvaluationReasoningGenerator` | 규칙 기반 매칭 결과가 근거 생성에 그대로 전달되는지 |
| `EvaluationService` | 필수 조건 판정 → 점수 산출 → 판정(적합/부적합/정보 부족) 전체 흐름 |
| `UserProfileService` | 연관 엔티티 cascade 삭제 |

**외부 의존성 격리**

- LLM 호출은 `LlmClient` 인터페이스를 통해 이루어지며, 테스트에서는 고정 응답 구현체(`FakeLlmClient`) 또는 `@MockitoBean`으로 대체합니다. 실제 API를 호출하는 통합 테스트는 `@Disabled`로 분리했습니다.
- 마감일 판정은 `Clock`을 주입받아 처리하므로, 테스트에서 기준 시각을 고정할 수 있습니다. 시간이 지나도 테스트 결과가 달라지지 않습니다.

```
DB_PASSWORD=your_password
OPENAI_API_KEY=your_api_key
```

**2. DB 실행**

```bash
docker compose up -d
```

**3. 애플리케이션 실행**

**4. 프론트엔드 실행**

```bash
cd frontend
npm install
npm run dev
```

## 설계 결정 기록

### 공고 수집 방식

당초 사람인 Open API를 통한 자동 수집을 계획했으나 승인이 나지 않았습니다.
공고를 크롤링하는 방법도 검토했지만, 채용 사이트 약관과 데이터 권리 문제가 있어
공식 경로가 아닌 수집은 하지 않기로 했습니다.

대신 실제 공고를 직접 옮겨 담은 seed 데이터셋을 공고 등록 API(`POST /api/jobs`)로 입력합니다.
공고는 출처(`source`)와 원본 ID(`externalId`)의 복합 유니크 제약으로 저장해 같은 공고가
중복으로 쌓이지 않으며, 데이터가 어디서 오든 같은 등록 경로를 거치므로 적합도 판단 로직은
출처와 무관하게 동작합니다. 외부 API를 연동하게 되면 등록 경로 앞단에 출처별 수집기를
추가하는 방식으로 확장할 수 있습니다.

프로젝트의 핵심 가치는 공고 데이터의 출처가 아니라 **적합도 판단과 근거 제시**에
있으므로, 이 결정이 프로젝트 목표를 훼손하지 않는다고 보았습니다.

### LLM과 규칙 기반의 역할 분리

LLM에 점수 산출을 맡기면 동일 입력에서도 결과가 흔들립니다.
따라서 LLM은 **입력 정제와 출력 설명**만 담당하고, 판정과 계산은 규칙 기반이 수행합니다.

| 담당 | 역할 |
|---|---|
| LLM | 공고 원문에서 요구 기술·자격증·경력 조건·직무 분류 추출, 판단 근거 문장 작성 |
| 규칙 기반 | 필수 조건 판정, 기술 매칭, 항목별 점수 계산, 가중치 적용, 근거의 충족·미충족 판정 |

근거 생성도 LLM이 충족 여부를 직접 판단하지 않고, 규칙 기반으로 계산한 일치·불일치 목록을
받아 문장으로만 정리합니다. (아래 트러블슈팅 "판단 근거와 점수의 불일치" 참고)

이 구조 덕분에 동일 요청을 반복해도 종합 점수가 소수점까지 일치합니다.

**LLM 도입으로 해결된 것**

규칙 기반(정규식) 파싱만으로는 다음을 처리할 수 없었습니다.

| 사례 | 규칙 기반 | LLM |
|---|---|---|
| 우대사항 목록에 섞인 "OPIC 제출 필수" | 탐지 불가 | `requiredCertificates: [OPIC]` |
| 개발 직군이 아닌 공고 (호텔 채용) | 판정 불가 | `jobCategory: OTHER` |
| "MSA", "코어뱅킹" 등 비기술 용어 혼입 | 기술로 오인 | 제외 |
| "3년 이하" vs "5년 이상" | 표현 변형에 취약 | `maxYears` / `minYears` 구분 |

**장애 대응과 비용 관리**

`LlmClient`를 인터페이스로 분리해, LLM 호출이 실패하면 기존 정규식 파서로 fallback합니다.
추출 결과는 DB에 저장하여 동일 공고에 대한 중복 호출을 방지합니다.
단, fallback으로 생성된 결과는 캐싱하지 않습니다. 일시적 장애로 얻은 저품질 결과가
영구히 고착되는 것을 막기 위해서입니다.

프롬프트에 "개념어는 제외하라"는 규칙이 있어도 "비동기 프로그래밍", "데이터 시각화" 같은
역량 표현이 기술 목록에 섞이는 경우가 있었습니다. 이런 표현은 사용자 기술명과 일치할 수 없어
무조건 감점으로 이어지므로, 추출 직후와 캐시 조회 시점 모두에 코드 기반 필터를 적용합니다.

추출 캐시는 `prompt_version`으로 관리합니다. 캐시의 버전이 현재 추출 프롬프트 버전과 다르면
재추출하고, 재추출이 실패하면 옛 버전 캐시를 그대로 사용합니다. 장애 중에는 옛 추출 결과가
정규식 fallback(기술·직무 분류 없음)보다 훨씬 정확하기 때문이며, 정규식 fallback은 캐시가 아예
없을 때만 사용합니다.

판단 근거(`checkPoints`)도 (공고, 프로필, 프로필 내용 해시, 추출 결과 해시, 근거 프롬프트 버전)을
키로 캐시합니다. 가중치는 키에 포함하지 않으므로, 가중치만 바꿔 재평가할 때는 근거를 다시 만들지 않습니다.

`LlmCallBreaker`는 한 번의 평가 안에서 LLM 호출이 연속 2회 실패하면 남은 공고에 대한 LLM 호출을
중단하고, 바로 옛 버전 캐시나 정규식 fallback으로 넘어갑니다. 크레딧 소진(429)처럼 다시 불러도 실패할
상황에서 남은 공고마다 실패할 호출을 반복하지 않기 위해서입니다.

**캐싱 효과 실측** (공고 24~28개, `gpt-4o`, Render 무료 플랜)

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 요건 추출 캐싱 — 재평가 시 LLM 호출 | 24회 | 4회 |
| 요건 추출 캐싱 — 평가 응답 시간 (3회 평균) | 52.6초 | 33.4초 |
| 근거 캐싱 — 평가 1회 LLM 호출 | 28회 | 0회 |
| 근거 캐싱 — 가중치만 바꿔 재평가 시 LLM 호출 | — | 0회 |

## 트러블슈팅

### LLM 출력의 불안정성

`gpt-4o-mini`로 시작했으나 적합/부족 항목 분류가 호출마다 뒤바뀌는 문제가 있었습니다.
보유하지 않은 기술을 "충족"으로 판정하거나, 요구 기술이 없는 공고에서 근거를 지어내는
사례가 반복되었습니다.

프롬프트에 판정 규칙을 명시적으로 추가하자 이번에는 반대 방향의 문제가 나타났습니다.
매칭 자체를 거의 수행하지 못하고 대부분을 "부족한 점"으로 분류하는 과도한 보수화였습니다.

프롬프트 조정만으로는 한계가 있다고 판단해 모델을 `gpt-4o`로 상향하고
`temperature`를 0으로 설정한 뒤 분류 정확도가 안정화되었습니다.
다만 완전한 결정론적 동작은 확보하지 못했으며, 추출 결과를 캐싱하여
동일 공고에 대한 판정이 유지되도록 보완했습니다.

### 읽기 전용 트랜잭션에서의 캐시 저장 실패

평가 조회 서비스는 클래스 레벨에 `@Transactional(readOnly = true)`가 적용되어 있습니다.
PostgreSQL은 읽기 전용 트랜잭션을 세션 레벨에서 강제하므로,
추출 결과를 캐시에 저장하는 INSERT가 실패하는 문제가 있었습니다.

캐시 저장 로직에 `Propagation.REQUIRES_NEW`를 적용해 별도 트랜잭션에서
실행되도록 분리하여 해결했습니다.

### 시간에 의존하는 판정 로직

마감일 판정에 `LocalDateTime.now()`를 직접 사용하면 테스트가 실행 시점에 따라
결과가 달라집니다. 검증용 데이터셋의 마감일이 지나면 기대값이 모두 무효가 되는
문제도 있었습니다.

`Clock`을 빈으로 주입받도록 변경하고, 테스트에서는 `Clock.fixed()`로 기준 시각을
고정했습니다.

### 운영 환경에 남은 테스트용 고정 시각

데모 결과를 고정하려고 기준 시각을 프로퍼티(`JOBFIT_CLOCK_FIXED_INSTANT`)로 덮어쓸 수 있게
해 두었는데, 이 값(2026-08-06)이 dev 프로필과 배포 서버 환경변수에 그대로 남아 있었습니다.
그 결과 두 달 뒤 마감일이 지난 공고들이 모두 "지원 가능"으로 판정되었습니다.
에러 없이 결과만 틀리는 문제라 발견이 늦었습니다.

고정 시각 설정을 dev 프로필과 배포 환경에서 모두 제거하고, 시각 고정은 테스트 코드 안의
`Clock.fixed()`로만 하도록 정리했습니다. 또한 애플리케이션 시작 시 실제로 사용하는 `Clock`의
현재 시각을 로그로 남겨, 같은 문제가 생기면 로그 한 줄로 확인할 수 있게 했습니다.

### 판단 근거와 점수의 불일치

화면의 "적합한 점"에는 Spring Framework, RDBMS가 충족으로 표시되는데, 기술 점수는
12개 중 Java 하나만 일치한 8.3점으로 계산되는 공고가 있었습니다.
점수는 기술명을 문자열 그대로 비교했고, 근거 문장은 LLM이 별도로 판단했기 때문입니다.

기술명 별칭 정규화(`SkillAliasNormalizer`)를 도입해 기술·경험 점수와 근거 생성이 모두 같은
매칭 기준을 쓰도록 통일하고, LLM은 규칙 기반으로 계산한 일치·불일치 목록을 문장으로만
정리하도록 역할을 좁혔습니다. 또한 필수 기술이 없는 공고가 기술·경험 0점으로 감점되던 문제는
평가 제외와 가중치 재배분으로 해결했습니다.

### 공고 문구의 모호성

일부 공고는 자격요건과 우대사항이 한 섹션에 혼재되어 있어, 특정 항목이 필수인지
우대인지 사람이 읽어도 해석이 갈립니다. 예를 들어 우대사항 목록 안에
"OPIC 또는 TOEIC Speaking 점수 제출 필수"가 포함된 경우,
이를 지원 자격으로 볼지 가점 요소로 볼지 판단이 어렵습니다.

이러한 모호성은 LLM 추출 결과의 불안정성으로 이어졌습니다.
완전한 자동 판정보다는 `checkPoints`(확인 필요 항목)로 사용자에게 제시하고
최종 판단을 맡기는 방향이 적절하다고 보았습니다.

### IT 통합 공채가 OTHER로 분류되어 지원 불가 처리된 문제

한국언론진흥재단·국민은행의 IT 공채가 직무 분류 `OTHER`로 추출되어, 기술·경험 점수와 무관하게
지원 불가(UNFIT)로 판정되었습니다. 직무 분류 enum에 "IT 직군 통합 채용"에 해당하는 값이 없었고,
Structured Outputs 스키마가 null을 허용하지 않아 LLM이 맞지 않는 값 중 하나를 억지로 골랐기
때문입니다. 그 결과 실행마다 분류가 달라졌고, 한 번 틀린 값이 캐시에 고정되었습니다.

원인을 가르기 위해 같은 공고를 3회씩 재추출해, 매번 틀리는 경우(프롬프트 문제)와 가끔 틀리는
경우(LLM 출력 흔들림)를 구분했습니다.

`IT_GENERAL` 값을 추가하고 스키마에서 null을 허용했습니다. 또한 캐시 저장 전에 규칙 기반 가드를 두어,
`OTHER`인데 공고에 IT 키워드나 추출된 기술이 있으면 판정 불가(null)로 낮춰 지원 불가로 떨어지지
않게 했습니다. 이미 고정된 틀린 캐시는 `prompt_version` 기반 무효화로 일괄 재추출되게 했고,
공고 하나만 다시 추출할 수 있는 강제 재추출 API(`POST /api/jobs/{id}/re-extract`)를 추가했습니다.

다만 일부 공고에서 기술이 필수에서 우대로 이동하는 등의 소수 차이는 남아 있습니다.
전체 재추출 비용에 비해 효과가 작다고 보아 보류했습니다.

## 알려진 한계

- 단일 사용자 프로필을 대상으로 동작합니다. 인증을 구현하지 않아 프론트엔드가 빌드 시 환경변수(VITE_USER_PROFILE_ID)로 지정한 프로필을 사용하며, 인증 도입 시 세션 기반 조회로 대체 가능한 구조입니다.
- 공고 원문의 서술 방식에 따라 LLM 추출 품질이 달라집니다. 기술 스택이 별도 섹션으로 정리된 공고와 업무 설명에 녹아 있는 공고의 추출 정확도에 차이가 있습니다.
- 캐시가 없는 첫 평가(또는 프롬프트 버전 변경 직후)에는 공고 수만큼 LLM을 호출하므로 응답에 시간이 소요됩니다.
- 필수 기술이 없는 공고는 우대 항목만으로 점수가 계산되므로, 평가 항목이 많은 공고와 점수의 의미가 다를 수 있습니다. 이런 공고는 카드에 평가 범위를 함께 표시합니다.
- 기술명 별칭은 직접 관리하는 사전 기반이라, 새로운 표기가 등장하면 사전에 추가해야 합니다.

## 향후 확장

- **공고 등록 자동화** — 공고 원문 텍스트를 입력받아 LLM으로 구조화하는 엔드포인트 추가. 다건 일괄 등록을 지원하여 수동 입력 비용을 줄일 수 있음
- 복수 채용 플랫폼 연동 및 중복 공고 판별
- 사용자 행동 기반 가중치 자동 조정
- IT 외 직무별 평가 전략 추가 (현재는 개발 직무 특화)
- CI 파이프라인 구성으로 push 시 테스트 자동 실행
